## 課題1：XSS

**ファイル:** `app/public/app.js` の `【課題1】`

### 修正前（脆弱）

```js
row.innerHTML = `<span class="time">${m.created_at}</span>
                 <span class="name">${m.username}</span>
                 <span class="body">${m.content}</span>`;
```

### 修正後（安全）

`innerHTML`（HTMLとして解釈）をやめて、`textContent`（ただの文字）で組み立てる：

```js
const time = document.createElement('span');
time.className = 'time';
time.textContent = m.created_at;

const name = document.createElement('span');
name.className = 'name';
name.textContent = m.username;

const body = document.createElement('span');
body.className = 'body';
body.textContent = m.content;   // ← ここが肝。文字は文字のまま表示される

row.append(time, name, body);
```

### なぜ防げる？

`textContent` は、渡した文字列を **100%ただの文字として表示**する。
`<img src=x onerror=...>` と投稿されても、`<` や `>` は「小なり・大なり記号」として
画面に出るだけで、**HTMLタグやスクリプトとしては解釈されない**。

> ポイント：ユーザー入力をHTMLとして描画しない。どうしてもHTMLに埋めるならエスケープする。
> Reactなどが比較的安全なのは、既定でこのエスケープを自動でやってくれるから
> （ただし `dangerouslySetInnerHTML` を使うと今回と同じ穴が空く）。

## 課題2：CSRF

**ファイル:** `app/server.js` と `app/public/app.js` の2か所

### 修正前（脆弱）

`server.js`：状態を変える操作なのに **GET** で受けている。

```js
app.get('/api/messages/delete-all', (req, res) => {
```

`app.js`：削除は fetch で送っているが、**GET のまま**（罠ページからも呼べる）。

```js
$('#deleteAllLink').addEventListener('click', async (e) => {
  e.preventDefault();
  await fetch('/api/messages/delete-all'); // ← GET なので別サイトから発火できる
  renderMessages();
});
```

### 修正後（安全）

**手順1: `server.js` を GET → POST に変える**

```js
app.post('/api/messages/delete-all', (req, res) => {
```

**手順2: `app.js` の `fetch` に `{ method: 'POST' }` を足す**

```js
$('#deleteAllLink').addEventListener('click', async (e) => {
  e.preventDefault();
  await fetch('/api/messages/delete-all', { method: 'POST' }); // ← POST にする
  renderMessages();
});
```

### なぜ防げる？

- 罠ページは `location.href = '.../delete-all'` で**トップレベルのGET**を送ってくる。
  削除を **POST 限定**にすれば、このGETは届かなくなる（404）。
- では攻撃者がPOSTフォームを送ってきたら？ → **ブラウザの既定 `SameSite=Lax`** が、
  **別サイトからのPOSTにはログインCookieを付けない**。だからサーバーは未ログイン扱いで弾く。
  （このアプリは `server.js` のログインで `sameSite: 'lax'` を明示的に設定済み）

> ポイント：**状態を変える操作は必ずPOST（などGET以外）**。GETは「見るだけ」に使う。

### さらに堅くするなら（余裕がある人向け）

SameSite だけに頼らず、**CSRFトークン**でも守るのが本番の定石：

1. ログイン時にランダムなトークンを発行してユーザーに渡す
2. 状態変更リクエストにそのトークンを必ず添付させる
3. サーバーは**トークンが一致するリクエストだけ**を受け付ける

罠ページは正しいトークンを知りようがないので、攻撃が成立しなくなる。
（有名なフレームワークは、この仕組みを標準で用意していることが多い）

## 課題3：SQLインジェクション

**ファイル:** `app/server.js` の `【課題3】`

### 修正前（脆弱）

```js
const sql = `SELECT * FROM users WHERE username = '${username}' AND password = '${password}'`;
const user = db.prepare(sql).get();
```

### 修正後（安全）

```js
const user = db
  .prepare('SELECT * FROM users WHERE username = ? AND password = ?')
  .get(username, password);
```

### なぜ防げる？

`?`（プレースホルダ）を使うと、`username` の中身は**必ず「ただの値」として扱われる**。
`admin' --` と入れても、それは「`admin' --` という名前のユーザーを探す」だけになり、
SQL文の構造（`--` でコメントアウトする、など）には**絶対に影響しない**。

> ポイント：入力を「SQL文の一部（＝コード）」ではなく「値（＝データ）」として渡す。
